TYAM — โครงสร้างการค้า 3 ชั้น (Trade Flow)

หนูลองโยง flow ที่พี่เล่าให้ฟังออกมาเป็นภาพค่ะ — brand-first b2b2c: ข้อมูลแม่แบบสินค้า (reference) ไหล ลงจากบนลงล่าง, การมองเห็น (visibility) ไหล จากล่างขึ้นบน. ด้านล่างมีตารางเทียบกับ schema ที่ทีมทำไว้แล้ว + คำถามที่จะถามพรุ่งนี้

1 โครงสร้าง 3 ชั้น + Customer
reference ออกจาก Layer 1 เท่านั้น → ส่งต่อลงล่าง. Layer ล่างเห็น Layer บนทีละชั้น (ไม่ข้าม).
reference / สินค้า ไหลลง ↓ (Layer 1 เป็นแหล่งเดียว)
การมองเห็น ↑ (ลูกค้าเห็น L3 → L3 เห็น L2 → L2 อาจเห็น/ไม่เห็น L1)
LAYER 1 Supplier — เจ้าของ brand (ต้นน้ำ) brand owner / โรงงานที่มี brand / โรงแรม (brand + location)
  • สร้าง reference / master product — คนเดียวที่ทำได้
  • กำหนด size / variant ที่ขายได้ (เช่น กาแฟ 250g / 500g)
  • กำหนด brand, หมวดหมู่, เอกสาร อย./certificate
  • approve Dealer ที่ขอมาขายสินค้าตัวเอง (deal กันเอง)
  • โรงงานรับจ้างผลิต (OEM) ที่ไม่มี brand → approve ไม่ได้ ("หลุด" ออกจากโมเดล)
  • มี dashboard เห็นยอด/ข้อมูลสินค้าตัวเอง
▼   reference + size ที่ "lock" แล้ว ส่งต่อให้   ▼
LAYER 2 Dealer — ตัวกระจาย / จุดยืดหยุ่น "ไม่ได้เป็นหน้าร้าน" — เป็นชั้นกลางที่จัดการเบื้องหลัง
  • ดึงสินค้าจาก Layer 1 หลายเจ้า มารวมเป็นคลังของตัวเอง
  • จัดการ ขนส่ง (logistics) + การตลาด + คุยดีล
  • ดู influencer + ตั้งค่า commission ให้ influencer
  • ปรับ รูป / การนำเสนอ ให้น่าสนใจ
  • เปลี่ยน brand ไม่ได้
  • เปลี่ยน / สร้าง size ใหม่ไม่ได้ (เลือกได้แค่ว่าจะขาย variant ไหนที่ L1 มี)
▼   ปล่อยให้ Layer 3 เป็นคนขายจริงต่อหน้าลูกค้า   ▼
LAYER 3 Influencer / Shop — หน้าร้านที่ลูกค้าเห็น storefront จริง
  • ปักตะกร้าได้เลย ไม่ต้อง approve (ถ้า Dealer เปิด is_pinnable)
  • ลงคลิป / นำเสนอสินค้าในวิดีโอ
  • ได้ commission แบบ last-click 7 วัน
  • มี dashboard เห็นยอด/ข้อมูลของตัวเอง
▼   ลูกค้าเห็น & ซื้อ   ▼
CUSTOMER ผู้ซื้อ เห็นเฉพาะ Layer 3 (หน้าร้าน)
  • ดูคลิป → เห็นสินค้าที่ปักตะกร้า → ซื้อได้เลย
  • ลงคลิปได้ถ้าเป็น Creator

⚠️ หมายเหตุที่ต้องถามพี่: ในข้อ "Layer 3 = หน้าร้าน, Layer 2 ไม่ใช่หน้าร้าน" — schema ปัจจุบันมอง Dealer (L2) เป็นผู้ขาย/ผู้รับเงิน/ผู้จัดส่งตามออเดอร์ ส่วน Influencer (L3) เป็นแค่คนพาลูกค้ามารับ commission ดูข้อ 4 (คำถาม D1) ด้านล่าง

2 การมองเห็นระหว่างชั้น (Visibility)

มองทีละชั้น — ไม่ข้าม

👤 Customer  → เห็น  Layer 3
🛍️ Layer 3  → เห็น  Layer 2
📦 Layer 2  → อาจเห็น / ไม่เห็น  Layer 1
(เพราะ L1↔L2 ส่วนใหญ่ deal กันแบบ offline มากกว่า online)

แต่ทุกชั้นมี dashboard ของตัวเอง

L1 / L2 / Influencer ต่างเห็น ข้อมูลสินค้า + ยอดขายของตัวเอง ผ่าน dashboard แยกตาม scope

📌 ใน schema ตอนนี้ visibility ยังไม่ได้ถูก encode ที่ DB — เป็นเรื่อง app-layer (RBAC + query WHERE supplier_id/dealer_id = $1). ต้องถามพี่ว่าต้องการกันถึงระดับ DB ไหม (คำถาม D4)

3 ความยืดหยุ่น — 1 entity สวมหลายหมวก
หัวใจของโมเดล: SME รายเดียวอาจเป็นทั้ง L1 + L2 + L3 พร้อมกัน

กรณีที่พี่ยกตัวอย่าง

L2 → ดึง L1 หลายเจ้า: Dealer เอาสินค้าจาก Supplier หลายราย มารวมเป็นร้านตัวเอง แล้วปล่อยให้ "ร้านตัวเอง" ใน L3 ขาย
Shop SME → ผสมเอง: shop ใน L3 ไปหยิบสินค้าจาก L2 หลายๆ ที่ มาประกอบขายในร้านตัวเอง
Brand owner ตัวเล็ก: SME สร้าง brand เอง (L1) + ทำหน้าที่ L2 เอง + ขายเอง (L3) เพราะไม่ใช่โรงงานใหญ่

⚠️ จุดที่ต้องคุยกับพี่

schema ปัจจุบัน 1 account = 1 role เท่านั้น (users.primary_role IN ('supplier','dealer','customer')) — supplier กับ dealer ควบในบัญชีเดียวยังไม่ได้

(Customer สวม flag is_influencer / is_creator เพิ่มได้ แต่ supplier↔dealer สลับไม่ได้)

→ ต้องถามว่า "หลายหมวก" = 1 login เห็นหลาย portal หรือ 1 นิติบุคคลเปิดได้หลาย account? (คำถาม D2)

4 เทียบกับ schema ที่ทีมทำไว้แล้ว
✅ = schema รองรับแล้ว   |   ⚠️ = รองรับบางส่วน / ต้องยืนยัน   |   ❌ = ขัด หรือ ยังไม่มีใน schema
กฎที่พี่สื่อ สถานะ หลักฐานใน schema
reference/master สร้างจาก L1 (Supplier) เท่านั้น ✅ products.supplier_id NOT NULL; Dealer ทำได้แค่ dealer_products (FK → products)
L1 เป็นคนกำหนด size / variant ✅ ตรงเป๊ะ product_variants เป็นของ Supplier; dealer_product_variants เลือกจาก master เท่านั้น (สร้างใหม่ไม่ได้)
L2 เปลี่ยน brand ไม่ได้ ✅ products.brand_id = lock field; dealer_products ไม่มี brand column
L2 เปลี่ยน size ไม่ได้ ✅ Dealer แก้ได้แค่ราคา/stock/SKU ของ variant ที่ master มี
L2 influencer + ตั้ง commission ✅ dealer_product_commissions.default_rate + influencer_commission_overrides.override_rate
L2 ดึงสินค้าจาก L1 หลายเจ้ามารวมร้าน ✅ dealer_products UNIQUE(dealer_id, product_id) — 1 Dealer ลงได้หลาย product จากหลาย supplier
L1 ↔ L2 deal กันเอง (Supplier approve Dealer) ✅ dealer_product_applications.approved_by → supplier_staff.id (Supplier approve ไม่ใช่ Admin)
L3 (Influencer) ปักตะกร้าได้เลย ไม่ต้อง approve ✅ dealer_products.is_pinnable DEFAULT true; is_influencer flag
L2 "ปรับรูปเท่านั้น" ⚠️ ปรับรูปได้จริง แต่ schema ยังเปิดให้ override name, description, SEO ด้วย — ขัดกับคำว่า "เท่านั้น"
Multi-role: 1 entity = L1+L2+L3 พร้อมกัน ❌ users.primary_role เลือกได้ role เดียว — supplier+dealer ควบกันไม่ได้
L2 ไม่ใช่หน้าร้าน, L3 คือหน้าร้าน ❌ ขัด order_groups.dealer_id = ผู้ขาย/ผู้จัดส่งตามออเดอร์; Influencer เป็นแค่ attribution บน order_items.influencer_id
Visibility chain (L2 อาจไม่เห็น L1) ⚠️ app-layer schema ไม่ได้ encode visibility — ไม่มี RLS / view ซ่อน supplier_id
Brand gate: ต้องเป็นเจ้าของ brand จริง (กัน OEM) ⚠️ policy brands ไม่มี owner/supplier_id — เป็น onboarding policy (มี business_verifications รองรับ)
5 คำถามที่จะถาม
เรียงตามความสำคัญ — 2 ข้อแรกกระทบ schema ใหญ่ ต้อง resolve ก่อนวาด/สร้างจริง
D1 · กระทบ Order schema มากสุด

"หน้าร้าน" ที่พี่บอกว่า L3 เป็น แต่ L2 ไม่เป็น — หมายถึง ใครรับเงิน / ออกใบเสร็จ / รับผิดชอบจัดส่ง หรือแค่ UI ที่ลูกค้าเห็น?

ตอนนี้ schema ให้ Dealer (L2) เป็นผู้ขายตามออเดอร์ (order_groups per Dealer), Influencer (L3) เป็นแค่คนพาลูกค้ามารับ commission. ถ้าพี่หมายถึง UI เฉยๆ → schema ยังไหว. ถ้าหมายถึง L3 ต้องเป็นผู้ขาย/รับเงินจริง → ต้องรื้อ order_groups.
D2 · กระทบ IAM

"1 entity สวมหลายหมวก (L1+L2+L3)" หมายถึง 1 login เห็นหลาย portal หรือ 1 นิติบุคคลเปิดได้หลาย account?

ตอนนี้ 1 account = 1 role (supplier / dealer / customer เลือกได้อันเดียว). ถ้าต้องการ 1 login หลาย role → ต้องออกแบบ IAM ใหม่ (membership / org-role table แทน single primary_role) — เป็น decision ใหญ่.
D3 · ตั้งใจหรือเปล่า

Dealer (L2) ควรแก้ ชื่อสินค้า + คำอธิบาย ได้ไหม หรือ lock ให้แก้ได้แค่ รูป + การตลาด เท่านั้น?

พี่พูดว่า "ปรับรูปเท่านั้น" แต่ schema เปิดให้แก้ name / description / SEO ด้วย. ถ้า lock เพิ่ม = ต้องแก้ schema.
D4 · scope การออกแบบ

การ "ซ่อน L1 จาก L2" เป็นแค่ ไม่โชว์ใน UI (ทำใน app ได้เลย) หรือต้องการ กันถึงระดับ database?

social-commerce ส่วนใหญ่ทำ app-layer พอ — ยืนยันเพื่อจะได้ไม่วาด schema-level gate ที่ไม่จำเป็น.
D5 · ยืนยันความเข้าใจ

size/variant ที่ L1 กำหนด (กาแฟ 250g/500g) — L2 เลือกได้ว่าจะขาย variant ไหนบ้าง (ขายแค่ 250g ก็ได้) แต่ สร้างไซส์ใหม่ไม่ได้ — เข้าใจถูกไหม?

schema เป็นแบบนี้อยู่: dealer_product_variants เลือกจาก master. ✅
D6 · onboarding policy

การกัน "ต้องมี brand จริง กัน OEM" — ให้ Admin review ตอน onboard (มี business_verifications แล้ว) พอไหม หรืออยากผูกข้อมูล brand↔supplier ในระบบจริงๆ?
